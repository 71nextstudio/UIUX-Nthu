Unit 02

The Big Picture

介面只是旅程中的
一個接觸點

使用者的體驗可能從搜尋、詢問朋友開始，跨過網站、App、Email 與現場服務，最後才形成「這個產品好不好用」的整體感受。

  • Journey Map 幫助團隊拉遠鏡頭，看見跨時間、跨通路的完整經驗
  • 不是先問「這頁怎麼畫」，而是先問「使用者一路上發生了什麼」

Unit 02

Definition

什麼是用戶旅程地圖？

用時間軸視覺化一位特定使用者，為了完成某個目標所經歷的階段、行動、想法、情緒與接觸點，並從中找出改善機會。

  • 主角必須明確：誰正在經歷這段旅程？
  • 情境必須具體：他在什麼狀況下，想完成什麼目標？
  • 每張地圖只描述一個觀點，避免把所有人混成「平均使用者」

「顧客旅程」常用於購買與服務關係，「用戶旅程」常用於產品使用；方法相同，本課程依情境選詞。參考：NN/g · Journey Mapping 101

Journey Map 不靠想像
它靠證據拼出旅程

Unit 02
Current-state vs. Future-state

先理解現在
再設計未來

Current-state · 現況旅程描繪今天真實發生的行動、想法、情緒與接觸點，用證據定位斷點、甜點與痛點。
Future-state · 未來旅程把優先機會轉成理想體驗，說明未來希望使用者如何更順利、更安心地完成目標。
先別混在一起現況寫「已知事實」；未來寫「設計假設」。混在一起會讓團隊誤判證據。
共同語言兩張地圖讓設計、PM、工程與服務人員看見差距，對齊改善位置與責任。

Unit 02

Breadth × Depth

先決定要畫多寬
再決定每一格要多深

Breadth · 廣度旅程跨多久、幾個階段、哪些通路？例如「第一次找牙醫到完成看診」或只看「線上預約」。
Depth · 深度每階段要記錄哪些層次？行動、想法、情緒、接觸點、證據、痛點與機會。
太寬的風險「從認識品牌到忠誠」容易變成空泛長表，細節不足以支持設計決策。
太深的風險把單一畫面操作拆得過細，會退化成 User Flow，失去跨通路與情緒脈絡。

判斷標準：這個範圍是否足以回答研究問題，又能讓團隊採取下一步？

Unit 02

Journey vs. Flow

Journey 看整體經驗
Flow 看產品內的操作

比較User JourneyUser Flow
視角宏觀：跨時間、跨通路的完整經驗微觀：一個產品內的具體任務步驟
內容行動、想法、情緒、接觸點與機會操作、畫面、判斷點與系統回應
時間可能跨數天、數週或更久通常是幾分鐘到幾小時
用途理解問題與尋找改善方向規劃與檢查任務流程

Unit 02

Anatomy

完整 Journey Map
至少有五個元素

  • Actor：一位明確的 Persona 或使用者觀點
  • Scenario + Expectations：具體情境、目標與期待
  • Journey Phases：旅程的高層階段
  • Actions, Mindsets, Emotions：做什麼、想什麼、感受什麼
  • Opportunities：洞察、改善機會、負責人與衡量方式

五個元素整理自 NN/g Journey Mapping 101；版面可依研究目的增減欄位，但主角與情境不能消失。

Element 01 · Actor

一張地圖，只放一個主角

同一個服務，不同 Persona 會有不同目標、資訊需求與情緒曲線。把他們混在一起，最後只會得到一條沒有人真正走過的旅程。

  • 寫下 Persona 名稱、目標、關鍵情境與限制
  • 行動與想法應來自研究資料，不是為了填滿格子而想像
  • 若要比較兩種族群，畫兩張地圖，再找交集與差異

Element 02 · Scenario

先把旅程的起點與終點說清楚

Unit 02

How to Read the Case

讀案例時，不只看格子
要看它如何推動設計

找跨階段痛點資訊不透明、等待不確定與術後資訊不足，是否在不同接觸點反覆出現？
看機會如何回應線上預約、候診狀態、白話說明與術後通知，是否直接對應痛點與情緒？
追到 Feature Breakdown案例把機會再拆成模組、優先級與 User Stories，示範研究如何接到產品規劃。
保持研究誠實這是一個結構參考；套用到專題前，仍要用自己的研究證據重畫內容。

練習：從案例挑一個 P1 功能，指出它對應哪個階段、哪個痛點、哪個期待結果。

Unit 02
Peak Moments

峰值是情緒最強烈的時刻

它可能是最高點，也可能是最低點。強烈情緒往往代表使用者的重要期待被滿足，或重要控制感被破壞。

  • 標出情緒轉折最大的階段，而不是只看最後結果
  • 追問「前一刻發生了什麼？」以及「使用者原本期待什麼？」
  • 不要把所有低點都當成同等嚴重；先判斷是否影響核心目標

本課程的「峰值」指旅程中的強烈情緒時刻，不等同於直接套用 Peak-End Rule。

Unit 02
Sweet Spots

甜點是值得保留與放大的
正向時刻

期待被確認使用者快速知道「這適合我」，不必猜測產品是否符合需求。
進度可預期清楚知道目前狀態、剩餘步驟與接下來會發生什麼。
被理解內容與服務回應了真實情境，而不是只講產品功能。
超出期待在關鍵時刻提供剛好的提醒、支援或選擇，降低不安。

甜點不是多加動畫或贈品；先找出使用者真正重視的價值，再決定如何放大。

Unit 02
Pain Points

痛點是阻礙目標的摩擦
不是所有抱怨的集合

  • 資訊難懂、比較標準不清楚、不知道下一步
  • 步驟過多、重複輸入、錯誤後無法恢復
  • 價格或規則不透明、狀態不確定、承諾前後不一致
  • 時間壓力、裝置限制、環境干擾、需要他人協助

寫痛點時補上「發生在哪一階段、造成什麼影響、有哪些證據」，才能進入優先排序。

Unit 02

5-Step Process

畫 Journey Map 的五個步驟

  • 確認研究目的：這張地圖要幫助團隊回答什麼問題？
  • 選 Actor 與 Scenario：一位主角、一個目標、清楚起訖點
  • 整理研究資料：把行動與接觸點依時間排列，再分成階段
  • 補上想法與情緒：標出高低點、甜點、痛點與證據缺口
  • 收斂機會與目標：決定先改善什麼、為誰改善、期待什麼結果

Unit 02

Interpretation

真正的工作從畫完之後開始

最大低點比較資訊分散，使用者需要自己記住與拼接，選擇焦慮升高。
正向轉折當費用、時數、作品要求被集中說清楚，使用者開始建立信心。
關鍵斷點付款後沒有即時確認，讓使用者懷疑是否成功，甚至重複操作。
資料缺口仍需確認「零基礎適配」與「時間投入」哪一項最影響決策。

Unit 02

Insight

洞察要說明「為什麼」
不能只重述痛點

證據使用者反覆切換頁面確認費用與時數
模式比較時需要自己記住分散資訊
原因第一次轉職，缺乏判斷課程價值的標準
洞察他需要的不是更多資訊，而是能放心做決定的比較框架

好洞察會改變團隊的理解：從「資訊不夠多」改成「缺少可用的判斷標準」。

Unit 02

Design Goal

設計目標描述體驗結果
不是直接指定功能

層級寫法判斷
太抽象「提升使用者體驗」不知道改善誰、哪個階段、什麼結果
太快跳功能「做一個課程比較按鈕」把解法當目標，限制後續發想
可行的目標「讓第一次轉職者能在比較階段快速理解差異，降低選擇焦慮並有信心進入報名」有對象、情境、改變與期待結果

句型：讓［目標使用者］在［旅程階段／情境］能［期待改變］，以達成［體驗結果］。

Unit 02

Prioritization

不是所有痛點都要立刻解決

使用者影響是否阻斷核心目標？發生頻率與情緒強度如何？
證據強度來自幾種資料？是否有一致模式？還只是團隊假設？
商業與風險是否影響轉換、信任、安全、法規或品牌承諾？
可行性與依賴需要哪些技術、內容、流程與跨部門協作？

先選 1–3 個最重要機會，讓下一單元的資訊架構有清楚方向。

AI Collaboration

但不能虛構旅程

  • 把訪談逐字稿依時間順序整理成行動、想法、情緒與接觸點
