# Nielsen 十大易用性原則（Unit 06）

1994 年由 Jakob Nielsen 提出的啟發式評估框架。3–5 位評估者即可找出約 75% 的易用性問題。

| 代碼 | 原則 | 檢查問題 |
|---|---|---|
| H1 | 系統狀態可見性 | 使用者知道「現在在哪／動作成功了嗎」？ |
| H2 | 現實世界對應 | 圖示和文字，非設計師的使用者也看得懂嗎？ |
| H3 | 使用者控制與自由 | 誤觸之後，使用者能輕易取消或返回嗎？ |
| H4 | 一致性與標準 | 同功能在不同頁面的位置、文字、顏色一致嗎？ |
| H5 | 錯誤預防 | 高風險操作有護欄（格式限制／二次確認）嗎？ |
| H6 | 辨識而非記憶 | 使用者不需記住前一頁資訊就能完成任務嗎？ |
| H7 | 彈性與效率 | 高頻使用者有更快完成任務的捷徑嗎？ |
| H8 | 極簡美學設計 | 每個元素都有必要存在嗎？有沒有干擾核心任務的贅語？ |
| H9 | 錯誤識別與修復 | 錯誤訊息有告訴使用者「哪裡錯／為什麼／怎麼修」嗎？ |
| H10 | 說明文件 | 使用者卡住時，能在 10 秒內找到有用的說明嗎？ |

---

## H1 系統狀態可見性
系統要在合理時間內用視覺回饋告訴使用者發生了什麼事。沒有回饋 → 使用者焦慮 → 反覆點擊 → 更多錯誤。
- **檢查**：按鈕按下後有 Loading／Pressed 狀態？送出後有成功或失敗訊息？長任務有進度條＋百分比或剩餘時間？導覽有標示目前所在位置？
- **好例子**：Gmail 寄信後的「郵件已傳送」Toast 加上「復原」；YouTube 上傳的進度條、百分比與剩餘時間。
- **紅旗**：按「確認轉帳」後頁面沒有任何反應，使用者會重複送出。

## H2 現實世界對應
使用使用者熟悉的語言、詞彙與隱喻，而不是系統術語。
- **檢查**：圖示有現實原型嗎？文案是使用者的語言還是工程師的語言？排列順序符合現實習慣（例如日期、地址格式）嗎？
- **好例子**：聽筒＝打電話、垃圾桶＝刪除、購物車＝待結帳；Google Maps 的「藍點＝你在這裡」。
- **紅旗**：顯示「HTTP 403 Forbidden」「ECONNREFUSED」「Null reference」。

## H3 使用者控制與自由
提供明顯的「緊急出口」，讓使用者敢大膽探索。
- **檢查**：有返回、取消、復原（Undo）？刪除先進垃圾桶？Modal 能用 ✕、Esc 或點背景關閉？取消訂閱和註冊一樣容易？
- **好例子**：Gmail 可調秒數的「復原寄送」；Mac 垃圾桶，永久清除才需二次確認。
- **紅旗**：取消訂閱藏在第 5 層選單，還要經過多個「保留訂閱」頁面（Dark Pattern）。

## H4 一致性與標準
相同的動作、詞彙、圖示在整個產品中保持一致，並遵循平台規範（iOS HIG／Material Design）。
- **檢查**：主要按鈕的位置、顏色、文字各頁相同？「確定／確認」「刪除／移除」用詞統一？返回鍵位置固定？
- **好例子**：iOS 全系統返回在左上角、右滑手勢；Google Workspace 各產品的「分享」按鈕完全相同。
- **紅旗**：購物頁「確定」在右、結帳頁在左；「取消」有時是按鈕、有時是文字連結。

## H5 錯誤預防
在可能出錯的地方加護欄，讓錯誤不會發生。優先順序：**限制 > 確認 > 修復**。
- **檢查**：用選擇器取代自由輸入（日期、國家）？輸入即時驗證？不可逆操作要二次確認或輸入名稱？危險按鈕與常用按鈕分開、外觀有區別？
- **好例子**：Google 日曆的日期選擇器不可能選到 2 月 30 日；GitHub 刪除 Repo 要手動輸入完整名稱。
- **紅旗**：Outlook「回覆」與「全部回覆」緊鄰且圖示相似。

## H6 辨識而非記憶
把選項、物件和動作可視化，讓系統記住，不要讓人記住。
- **檢查**：有自動完成、最近使用、搜尋建議？多步驟流程中，前一步的關鍵資訊仍可見？表單欄位的 Label 在輸入後仍然看得到（不要只用 placeholder）？
- **好例子**：Google 搜尋自動完成；Spotify 首頁的最近播放。
- **紅旗**：Windows「執行」視窗要使用者自己記住 `regedit`、`msconfig`。

## H7 彈性與效率
新手走寬路，專家走捷徑。
- **檢查**：有快捷鍵、批次操作、常用項目、個人化設定？高頻任務的步驟數合理？
- **好例子**：Figma 的 V／R／T 快捷鍵；VS Code 的 Command Palette。
- **紅旗**：每天用 200 次的 ERP 員工和第一次使用的人走完全一樣的長路徑。

## H8 極簡美學設計
每個元素都要有存在的理由。多餘資訊會稀釋重要資訊的能見度。
- **檢查**：首屏的核心任務一眼可見？有沒有重複的說明、裝飾性元素、搶焦點的廣告？
- **好例子**：Google 首頁只有 Logo、搜尋框和兩個按鈕；Apple 產品頁一個畫面只傳遞一個訊息。
- **紅旗**：早期 Yahoo 首頁把新聞、天氣、股市、廣告全塞在一起。

## H9 錯誤識別與修復
好的錯誤訊息 ＝ **問題是什麼 ＋ 為什麼 ＋ 怎麼修**，並用使用者看得懂的語言。
- **檢查**：錯誤訊息出現在出錯的欄位旁？附正確格式範例？保留已輸入的內容？404 頁有搜尋或回首頁的出口？
- **好例子**：Airbnb「請輸入有效的電子郵件地址，例如 name@example.com」；GitHub 404 頁有搜尋框和回首頁按鈕。
- **紅旗**：只顯示「Error 0x80070005」或「操作失敗」。

## H10 說明文件
最好的說明是「需要的當下，它就在那裡」，而且以任務為導向。
- **檢查**：空狀態有引導文字？複雜欄位旁有 ? 提示？說明可搜尋？
- **好例子**：Notion 空白頁的「輸入 / 以選擇區塊類型」；Figma UI 中的 ? 直接連到相關說明。
- **紅旗**：說明連結藏在頁尾 10px 灰字裡，或是一份 20 頁的技術 PDF。
