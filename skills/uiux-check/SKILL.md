# UI/UX Check

用三套規則審查介面，找出問題、說明依據、給出具體修正。報告一律用**繁體中文**。

## 規則來源（需要細節時才讀）

| 代碼 | 規則 | 參考檔 |
|---|---|---|
| H1–H10 | Nielsen 十大易用性原則（Unit 06） | `references/heuristics.md` |
| G1–G8、L1–L7 | 完形心理學、Laws of UX（Unit 07） | `references/gestalt-laws.md` |
| V-L、V-T、V-C、V-S | 版面、排版、色彩、一致性（Unit 08） | `references/visual-foundations.md` |

第一次執行時三份都讀；之後只讀和發現相關的那份。

## 流程

### 1. 確認審查對象與範圍
- 確認輸入類型，以及要審查的是**單一畫面**還是**一段流程**（例如註冊 → 驗證 → 完成）。流程類問題（H1、H3、H5、H9、L5）需要看到前後畫面。
- 使用者沒說時，預設三套規則全部檢查。使用者指定範圍（例如「只看色彩」）就只做那部分。

### 2. 依輸入類型取得證據

| 輸入 | 怎麼取得證據 |
|---|---|
| 截圖 / 圖片 | 直接看圖。間距、字級是**目測估計**，報告要標「約」。 |
| Figma 連結 | 有 Figma MCP 時：`get_screenshot` 看畫面，`get_design_context` / `get_metadata` 取精確數值，`get_variable_defs` 檢查是否使用 Variables。 |
| 網址 | 有瀏覽器工具時打開頁面截圖並讀取 computed style；沒有就請使用者提供截圖。 |
| HTML / CSS / React | 讀原始碼，執行 `scripts/css_audit.py <檔案或資料夾>` 抓間距、行高、字級種類與寫死色碼；有實際畫面更好。 |

**對比度一定要計算，不要目測**：
```bash
python3 ~/.claude/skills/uiux-check/scripts/contrast.py "#767676" "#FFFFFF"
python3 ~/.claude/skills/uiux-check/scripts/contrast.py "#F59E0B" "#FFFFFF" --large   # 大字門檻 3:1
```
截圖上取不到精確色碼時，寫出估計色碼並註明「估計值」。

### 3. 逐條檢查
- 依 references 裡每條規則的「檢查問題」逐一判斷：**符合 ✅／不符合 ❌／無法判斷 ➖**（缺少畫面或流程時）。
- 每個 ❌ 都要有**證據**：指出畫面上的具體元素、位置或數值，例如「結帳頁右上『取消』是灰色 12px 文字連結，對比 2.8:1」。沒有證據就不要列。
- 同一個問題同時違反多條規則時，合併成一筆，列出所有規則代碼。

### 4. 判定嚴重度

| 等級 | 意義 | 例子 |
|---|---|---|
| 🔴 嚴重 | 會讓使用者無法完成任務、做出不可逆的錯誤，或無法閱讀 | 刪除沒有確認、內文對比 < 3:1、送出後沒有任何回饋 |
| 🟠 中度 | 造成明顯的困惑、延遲或重複操作 | 錯誤訊息只寫「操作失敗」、同功能按鈕位置不一致 |
| 🟡 輕微 | 細節不一致或效率問題，不影響完成任務 | 間距 13px、圓角混用、Icon 線條粗細不一 |

### 5. 輸出報告

依下面的格式輸出。問題依嚴重度排序，同等級的依影響範圍排序。

```markdown
# UI/UX 檢查報告：〔畫面或產品名稱〕

**審查範圍**：〔畫面 / 流程〕 ・ **輸入**：〔截圖 / Figma / 程式碼〕 ・ **數值精確度**：〔精確 / 目測估計〕

## 總覽
| 類別 | 符合 | 不符合 | 無法判斷 |
|---|---|---|---|
| 易用性 H1–H10 | 7 | 2 | 1 |
| 完形與 UX 法則 | … | … | … |
| 視覺基礎 | … | … | … |

**最需要優先處理的 3 件事**：
1. …
2. …
3. …

## 問題清單
### 🔴 1. 〔一句話描述問題〕
- **規則**：H5 錯誤預防、L3 Fitts's Law
- **位置與證據**：〔具體元素、數值〕
- **影響**：〔使用者會遇到什麼〕
- **修正建議**：〔可以直接動手的做法，含數值，例如「改為 44×44 以上、與『全部回覆』間距 ≥ 16px」〕

### 🟠 2. …

## 做得好的地方
- 〔2–4 點，附規則代碼〕

## 逐條檢核
〔表格：代碼｜規則｜結果 ✅❌➖｜一句說明〕
```

## 判斷原則
- **修正建議要具體**：給數值、給元件、給文案範例。不要只寫「增加對比」「優化排版」。
- **區分規則與偏好**：只依規則判定問題。純屬美感偏好的意見放在報告最後的「其他建議」，不列入問題清單。
- **數值精確度要誠實**：截圖目測的間距與字級標「約」；能計算的（對比度）一定計算。
- **資訊不足就標 ➖**：例如單張截圖無法判斷 H3（能否返回）時，標 ➖ 並寫出還需要哪個畫面，不要猜。
- 使用者要求修改設計稿或程式碼時，先列出要改的項目並取得同意，再動手。
