Unit 04
IA

Definition

什麼是資訊架構？

Information Architecture 是決定「內容與功能如何被組織、命名、連結」的實務。它是產品的資訊骨幹，決定使用者能不能靠自己找到下一步。

  • 組織（Organization）：內容要分成哪幾群？依什麼邏輯分？
  • 命名（Labeling）：每一群要叫什麼名字？使用者看得懂嗎？
  • 關係（Relationship）：誰是誰的上層？哪些內容要交叉連結？
  • 尋找（Findability）：使用者要透過導覽、搜尋還是篩選抵達？
先把結構確定，Wireframe 才不用一直重畫——每次改導覽、改分類，畫面都要跟著改一次。這也是為什麼 IA 排在畫 Wireframe 之前。

Common Confusion

IA、導覽、Sitemap 不是同一件事

三個詞常被混用，但它們處在不同層次。搞混會讓討論一直卡住。

名詞它是什麼存在的位置典型產出
資訊架構 IA 底層的內容組織邏輯與命名規則，是一整套持續維護的實務。 看不見，在結構層。 分類原則、命名規範、內容模型。
導覽 Navigation 把 IA 呈現給使用者的一組 UI 元件，引導使用者抵達內容。 看得見，在介面層。 主選單、側欄、麵包屑、頁尾。
網站地圖 Sitemap 用節點與線條把網站結構「畫」出來的視覺文件，是 IA 的其中一個切片。 設計文件，不是產品本身。 Figma／FigJam 上的結構圖。
NN/g 的說法：A sitemap is only one part of the site's information architecture. 畫完 Sitemap 不等於 IA 做完了。

影片參考 · NN/g

資訊架構的三個關鍵模型

同一個產品的結構，可以用三種模型來描述。三者互補，不能互相取代。

① 底層 IA 結構 內容之間真正的層級與關係，是整個產品的資訊骨幹。使用者看不到它，但每個決策都被它決定。
② 分類法 Taxonomy 一套正式的分類與命名規則：類別、標籤、屬性、受控詞彙與 facet。有幕後的一面（後台 metadata），也有台前的一面（篩選器、標籤列）。
③ 導覽 Navigation 使用者實際接觸的 UI 元件。它是 IA 的「呈現方式」，只會露出結構的一部分。
課前／課後請看：Information Architecture — 3 Key Models（YouTube）。回家作業會用這三個模型去拆解一個真實網站。

Unit 04

Findability vs. Discoverability

使用者是「在找」還是「還不知道有」？

這兩件事需要不同的設計手法，混在一起談會做出錯的決定。

可尋性 Findability 使用者已經知道自己要什麼，問題是能不能找到。

對應設計：清楚的分類與標籤、搜尋、篩選、麵包屑。

檢驗方式：樹狀測試、任務式可用性測試。
可發現性 Discoverability 使用者不知道某個功能或內容存在。

對應設計：首頁曝光、引導、空狀態提示、推薦、新功能提示。

檢驗方式：觀察使用者是否從沒點過那個入口。
常見誤判：「使用者找不到 → 加一個搜尋框就好」。如果問題是可發現性，加搜尋框沒用——使用者根本不知道要搜什麼。

Information Scent

資訊氣味：使用者怎麼決定下一步

使用者不會讀完整頁再決定，而是像動物覓食一樣「順著氣味走」——從連結文字判斷點下去會不會離目標更近。

  • 氣味強：連結文字直接對應使用者心中的目標詞，例如「退貨與換貨」。
  • 氣味弱：模糊或行銷式用語，例如「服務中心」「了解更多」「探索」。
  • 氣味斷掉：點進去的內容跟連結文字不符，使用者會退回並失去信任。
實務含意：導覽的用字不是文案問題，是架構問題。命名錯了，結構再漂亮也沒用。

Unit 04

Structure Patterns

扁平 vs. 深層層級

沒有哪一種一定比較好，取捨在於「一次要看多少選項」與「要點幾次才到」。

結構特徵優點風險適合
扁平 Flat 層級少（1–2 層），每層選項多。 點擊次數少，內容一眼看得到，容易發現。 單層選項爆炸，掃視成本高，難以擴充。 內容量少、分類界線不清的產品。
深層 Deep 層級多（3 層以上），每層選項少。 每個決策簡單，分類乾淨，好擴充。 路徑長，中間層若命名不清就會迷路。 內容量大、分類邏輯明確的產品。
多數產品的答案是中間值：用巨型選單（Mega Menu）或左側垂直導覽，把深層結構在一個畫面裡攤開，同時保有分類與可掃視性。

Research → Features

從洞察到功能清單

每一個功能都要能回答一句話：它服務誰的哪個需求，證據在哪裡。沒有證據的功能，先放進待驗證區。

01 需求來自訪談逐字稿、旅程地圖上的痛點與甜點。
02 功能寫成「使用者可以做什麼」，動詞開頭。
03 證據標註來源：第幾位受訪者、哪個競品、哪段觀察。
04 優先級核心／次要／邊緣／不做，並寫下理由。

Card Sorting

卡片分類法

讓參與者把寫著內容或功能的卡片，分成他們覺得合理的群組。最常用在發想階段揭露使用者的心智模型，也能用封閉式去評估既有分類。

  • 發現使用者自然的分群邏輯，而不是你以為的邏輯。
  • 發現使用者實際使用的詞彙，作為導覽標籤的參考依據。
  • 找出被反覆放錯位置的項目——那通常代表命名有問題。
  • 成本低、不需要做出畫面，早期就能做。
產品設計流程
Unit 04

Open vs. Closed

開放式與封閉式卡片分類

開放式 Open 做法：參與者自由分群，並且自己替每一群命名。

回答：使用者怎麼看這些內容？他們會怎麼稱呼？

用在：從零開始建立 IA，還沒有分類方案時。
封閉式 Closed 做法：你先給定分類，參與者把卡片放進去。

回答：我這套分類，使用者放得進去嗎？

用在：已有分類草案，要驗證或改版既有 IA。
等一下的實作時間有限，只做開放式：看使用者怎麼自然分群。封閉式驗證留給有餘力的同學課後補做；混合式（Hybrid）則是給定分類但允許新增。

Unit 04

Process

卡片分類法四步驟

01 準備卡片一張卡片一個內容或功能。用使用者看得懂的詞，避免內部術語。建議 30–60 張。
02 招募參與者找目標使用者，不是找同組同學。開放式建議 15 人以上，課堂內至少 3–5 人。
03 進行分類不引導、不解釋卡片意思。請參與者邊分邊說出理由，這比結果更有價值。
04 分析結果找共通模式：哪些卡片總是被放在一起？哪些每個人放的位置都不同？
線上工具：Optimal Workshop、Maze、UXtweak；課堂內用 FigJam 便利貼就夠了。課堂用板（卡片已建好）：練習板；參考範例：1、2。

Unit 04

Pitfalls

卡片分類最容易做壞的地方

  • 卡片用詞洩題：卡片上直接寫「訂單查詢」「訂單取消」，參與者只是在做字詞配對，不是真的在分類。
  • 卡片比例失衡：某個功能區塞了 20 張卡，其他區只有 2 張，結果一定偏向那一區。
  • 卡片太多：超過 60 張參與者會疲勞、隨便分，品質急速下降。
  • 中途解釋卡片：一旦你開始解釋，你就把自己的心智模型灌給參與者了。
  • 只看結果不問理由：分群結果只是表面，「為什麼這樣分」才是可以拿來設計的東西。

分類做好了，要怎麼驗證？

樹狀測試把 UI 全部拿掉，只留純文字的層級結構，請使用者「去找某個東西」。找不到就是架構有問題，不能怪視覺。

Unit 04

Content Model

內容模型：每一頁到底裝了什麼

IA 決定內容放在哪裡；內容模型決定每一種內容由哪些欄位組成。它是 Wireframe 上每個區塊的依據。

內容類型 內容的類別。

例：課程、講師、評價、文章。
屬性 描述該類型的欄位。

例：課程名稱、時數、難度、價格、封面圖。
關聯 類型之間的關係。

例：一堂課屬於一位講師、可有多則評價。
元數據 用來組織與檢索的資料。

例：標籤、分類、上架日期。
實務價值：先寫清楚欄位，Wireframe 就不用再猜「這張卡片要放什麼」，也能直接讓工程師理解資料結構。

Unit 04

Labeling · 4 S's

標籤怎麼命名

NN/g 提出的四個原則，用來檢查你的導覽項目與連結文字。

  • Specific 具體：明確說出點下去會看到什麼。✕「服務」 ✓「維修預約」
  • Sincere 誠實：點進去的內容要與標籤承諾一致，不要標題殺人。
  • Substantial 充分：脫離上下文也看得懂。✕「了解更多」 ✓「查看退款條件」
  • Succinct 精簡：在滿足前三項的前提下越短越好——沒有字數上限，但不要多餘。

Unit 04

Terminology

先把四個詞分開

這四個在網路上常常混著用，開會的時候你講 A 對方想 B，討論就會空轉。

User Journey 跨通路、跨天數的高層目標。Unit 02 畫的旅程地圖就是這個。
User Flow 在單一產品內完成一個任務的步驟。等一下要畫的是這個。
Flowchart 表達 User Flow 的一種畫法，用方塊跟菱形，強在邏輯分支。
Wireflow 另一種畫法，用畫面縮圖取代方塊，強在看得到頁面長怎樣。
記法：Journey 是尺度，Flow 也是尺度；Flowchart 跟 Wireflow 是把 Flow 畫出來的兩種格式。

同一個外送 App，用旅程地圖看是「餓了到吃飽」，用 Flow 看是「打開 App 到按下送出訂單」。

Unit 04

Blind Spots

Flowchart 跟 Wireframe 各自看不到的東西

Flowchart 的盲點 邏輯分支寫得再完整，都沒有畫面脈絡。

「選擇付款方式」在圖上是一個方塊，但實際上是全螢幕的頁面、還是底部彈出的選單？使用者的感受差很多，圖上看不出來。
Wireframe 的盲點 版面畫得再清楚，都不擅長記錄互動。

尤其是頁面沒換、內容卻變了的情況：點篩選器之後商品列表就地更新，這在一張張靜態的 Wireframe 上根本表達不出來。
這兩個盲點合在一起，就是為什麼會有第三種東西：Wireflow。

Wireflow

Wireflow：把畫面塞進流程圖

節點不再是抽象的方塊，而是那個畫面本身。箭頭從「你點的那顆按鈕」出發，指向點完之後看到的東西。

看箭頭上的標籤：Select safe category、Button enabled、Choose avatar——每條線都寫了是什麼互動觸發的，不是只畫一條線。
也看編號：1 → 1.2 是同一個畫面選了分類之後的狀態，2 → 2.1 → 2.2 也是。用小數點區分「新畫面」與「同一畫面的不同狀態」，這是 Wireflow 最好用的地方。更多圖例見 NN/g 原文。

When to Use

那我到底該畫哪一種？

你的產品長這樣畫這個為什麼
頁面多、每頁內容相對固定的網站Wireframe重點在每一頁該放什麼，頁面之間的關係用 IA 圖表達就夠了
流程長、分支多、要窮盡記錄Flowchart邏輯分支是主角，畫面長怎樣先不重要
頁面少、但內容隨互動一直變的 AppWireflow不畫出畫面狀態，就講不清楚「哪裡變了」
你們的專題多半是第三種。所以今天的順序是：先用 Flowchart 把邏輯理清楚，再畫 Wireframe；把兩者合成 Wireflow 留給有餘力的同學課後練習。

Unit 04

Notation

Flowchart 只要記四個符號

不用背工程用的完整符號表。你們畫的流程，這四個就夠了。

◯ 起點／終點正式畫法是圓角矩形，課堂上畫成圓形也可以。使用者從哪進來、任務在哪算完成。一張圖只有一個起點，終點可以有好幾個。
▭ 動作／畫面使用者做的一件事，或看到的一個畫面。用動詞開頭：「輸入手機號碼」。
◇ 判斷點系統或使用者要做選擇的地方。裡面寫成是非題：「已登入？」
→ 路徑從判斷點出去的每條線都要標條件：是／否、成功／失敗。
最常見的錯：判斷點只畫「是」那條線。菱形只要有一條線出去，那它就不該是菱形。
範例板：Flow Chart 流程圖範例——有符號說明，以及「鬧鐘」與「會員登入」兩個完整流程可以照著看。（那份多示範了一個「資料輸出／輸入」的平行四邊形，你們用不到，看到不用理它。）

Anatomy

一條流程要交代三件事

◯ 起點：從首頁點「我的課程」 │ ▼ ┌──────────────┐ │ 顯示課程列表 │ └──────────────┘ │ ▼ ◇ 有進行中的課程嗎？ │ ├── 有 ──▶ 顯示上次看到第幾分鐘 ──▶ 點「繼續看」──▶ ◯ 終點：播放器開始播 │ └── 沒有 ─▶ 空狀態：「還沒開始任何課程」＋ 去逛課程的按鈕
  • 入口：使用者從哪裡進到這條流程？不只一個入口就全部畫出來。
  • 判斷點：中間哪裡會分岔？條件是什麼？
  • 終點：怎樣算「完成」？成功跟失敗要分開畫。

    Edge Cases

    你一定會漏掉的那幾條線

    畫 Flow 的時候，理想路徑十分鐘就畫完了。剩下的時間都花在這些上面——而評圖的時候問的也都是這些。

    • 沒資料：第一次使用的人打開這一頁，看到什麼？
    • 找不到：搜尋沒有結果、篩選之後一個都不剩，畫面怎麼辦？
    • 沒權限：沒登入、沒付費、帳號被停用，擋在哪一步？
    • 出錯：網路斷掉、付款失敗、上傳的檔案太大。
    • 要等：需要載入三秒以上的地方，等待中顯示什麼？
    • 反悔：中途想退出、想改剛剛填的東西，回得去嗎？
    練習的時候用這六條當檢查表，一條一條問自己「這個情況我畫了嗎」。

    Unit 04

    IA → Flow

    怎麼把 IA 圖變成流程

    IA 圖是靜態的地圖，Flow 是走過去的路線。地圖上你標的那條核心路徑，就是要先畫的那條 Flow。

    01 挑一條從 IA 圖上標了顏色的核心路徑挑一條，不要一次畫全部。
    02 拆步驟把這條路徑拆成使用者實際的動作，動詞開頭。
    03 找分岔每一步問一次「這裡會不會有人走不下去」，會的話就是判斷點。
    04 補例外拿前一頁的六條檢查表逐一補上。
    一堂課只要畫得完一條完整的核心路徑就夠了。畫三條半成品，不如一條把例外都補齊。

    Fidelity

    保真度不是一條刻度，是三條

    很多人以為保真度就是「畫得精不精緻」。其實是三個可以各自調整的維度，你可以視覺很粗糙但互動很完整。

    互動 Interactivity 低：需要有人在旁邊幫忙換畫面。
    高：連結跟選單真的點得下去。
    視覺 Visuals 低：手繪草圖、灰階方塊。
    高：完整的層級、間距、版面。
    內容 Content 低：摘要跟佔位符。
    高：真實的文案跟圖片。
    今天做的是：互動低、視覺低、內容中——文字用真的，因為假字看不出資訊夠不夠。

    Unit 04

    Trade-offs

    低保真跟高保真各自的好處

    低保真高保真
    做起來快，省下的時間可以多改幾輪慢，做一版就用掉不少時間
    測試中途當場拿筆改就好要回去改檔案，下一場才能用
    受測者反應壓力小，比較敢講難聽的話當成真的軟體在用，行為更真實
    能測到什麼概念、流程順不順、資訊夠不夠特定元件、可視線索、字好不好讀
    設計師心態還沒投入太多，願意打掉重來做很久了，捨不得改
    老闆的期待看得出還沒完成，預期會再改容易誤以為快做完了
    最後兩列是關鍵。高保真的成本不只是工時，還有你捨不得改的心理投入。

    Why Low-Fi

    今天不准上色

    不是為了為難你們。是因為視覺一上去，就沒有人會再討論結構了。

    • 畫面一漂亮，評圖的回饋就會全部集中在配色跟字體。
    • 結構的問題被掩蓋住，等到 Mockup 才發現，要重畫的量是現在的十倍。
    • 你自己也會捨不得——花三小時調好的版面，誰想砍掉重來。
    • 現在畫得越醜，後面改得越輕鬆。
    今天的規則：只能用黑、白、灰。要標重點的話，用一個藍色，就一個。

    Content

    Wireframe 上該放什麼

    要放 • 真實的標題與按鈕文字（「加入購物車」不要寫「按鈕」）
    • 資訊的先後順序與分組
    • 每個可以點的東西
    • 這一頁的主要動作，只能有一個最明顯
    • 空狀態、錯誤狀態的版本
    先不要放 • 顏色、漸層、陰影
    • 真實照片（用灰色方塊加一個叉）
    • 精挑的字體
    • 圖示的細節（畫個圈圈標「icon」就好）
    • 動畫與轉場
    文字一定要用真的。Lorem ipsum 會騙你——假字排起來永遠很整齊，真的標題塞進去才知道會不會爆版。

    Unit 04

    Checklist

    畫完一張，問自己這六題

    • 第一眼會看到什麼？那是這頁最重要的東西嗎？
    • 這一頁的主要動作是哪一個？它有比別的按鈕明顯嗎？
    • 使用者從哪裡來的？他知道自己在哪一層嗎？
    • 如果這裡沒有資料，畫面長什麼樣？
    • 按下去之後會發生什麼？成功跟失敗分別看到什麼？
    • 想回上一步的話，回得去嗎？
    六題都答得出來，這張 Wireframe 才算畫完。答不出來的那一題，通常就是流程圖上漏掉的那條線。

    Figma

    Auto Layout：讓版面自己會動

    沒用 Auto Layout 的時候，你改一個標題變兩行，下面所有東西都要手動往下推。用了之後，它們自己會讓開。

    沒有 Auto Layout 元素靠絕對座標擺放。

    加一個項目 → 手動推下面全部
    文字變長 → 手動改寬度
    要做手機版 → 幾乎整個重排
    有 Auto Layout 元素依方向、間距、內距自動排列。

    加一個項目 → 自己往下長
    文字變長 → 容器自己撐開
    要做手機版 → 改一下寬度就好
    快捷鍵：選好圖層按 ⇧ A（Windows 是 Shift A）就加上去了。移除是再加一個 ⌥／Alt。

    Flow Direction

    三種排列方向

    垂直 Vertical 沿 y 軸往下排。

    清單、表單欄位、卡片內部的標題與說明。
    水平 Horizontal 沿 x 軸往右排，可以設定換行（wrap）。

    按鈕列、標籤列、導覽項目。
    網格 Grid 排成行與列，格子可以跨欄。

    商品列表、儀表板。
    實務上幾乎都在巢狀：一張商品卡是垂直（圖／標題／價格），一排卡片是水平或網格。每一層各自有自己的間距設定。

    Spacing

    Padding 跟 Gap 差在哪

    兩個都是留白，差別在留在哪裡。這兩個搞混，版面就會怎麼調都不對。

    ┌─────────────────────────────────┐ ◀── 容器邊界 │ ↕ padding-top │ │ ┌─────────────────────────┐ │ │ │ 項目 A │ │ │ └─────────────────────────┘ │ │ ↕ gap │ │ ┌─────────────────────────┐ │ │ │ 項目 B │ │ │ └─────────────────────────┘ │ │ ↕ padding-bottom │ └─────────────────────────────────┘ ↔ padding-left padding-right ↔
    屬性是什麼可以怎麼設
    Padding容器邊緣跟裡面的東西之間的留白四邊統一、上下左右分開，或四個值各自設
    Gap between裡面的東西彼此之間的距離給固定數值，或設成 Auto 讓它們平均散開

    Unit 04

    Resizing

    Hug、Fill、Fixed

    這三個是 Auto Layout 最常卡住的地方。先記住一件事：Hug 只能給容器，Fill 只能給裡面的東西。

    模式能套在誰身上它會做什麼什麼時候用
    Hug contents只有 Auto Layout 容器縮到剛好包住裡面的東西按鈕：文字多長，按鈕就多寬
    Fill container只有子元件撐滿父容器剩下的空間輸入框：不管視窗多寬都填滿
    Fixed容器跟子元件都可以尺寸就是不變頭像、圖示這種固定尺寸的東西
    一定要記住這條規則：只要容器裡有任何一個子元件設成 Fill，容器在那個軸向就不再是 Hug，會自動變成 Fixed。「我明明設了 Hug 怎麼沒反應」，九成是這個原因。

    Unit 04

    Constraints

    那 Constraints 又是什麼

    Constraints 管的是「frame 被拉大拉小的時候，圖層要怎麼跟著動」。跟 Auto Layout 是兩套獨立的機制。

    設定水平方向的行為
    Left / Right跟左邊界（或右邊界）保持固定距離
    Left and Right兩邊都固定，所以圖層自己會跟著變寬變窄
    Center永遠對齊中線
    Scale尺寸跟位置都按比例縮放
    垂直方向同理：Top、Bottom、Top and Bottom、Center、Scale。
    重要：Auto Layout 容器裡的一般子元件用不了 Constraints——它們用的是 Hug／Fill／Fixed。只有設成 absolute position（Mac 按住 Ctrl 拖曳）跳出排列流程的元件，才會回到 Constraints。

    課堂練習 · 40 分鐘

    從卡片分類到第一張 Wireframe

    個人作業，用自己的專題。時間比原本的兩堂課壓縮很多，重點是走完整條流程，不是每一步都做到完美。

    Step 1 · 10 min用自己的功能清單做一輪快速卡片分類（開放式），整理出第一版 IA。
    Step 2 · 10 min從 IA 挑一條核心路徑，畫成 Flowchart，補上判斷點與至少 2 種例外路徑。
    Step 3 · 15 min用 Auto Layout 畫 1–2 張低保真 Wireframe，涵蓋流程的頭與尾。
    Step 4 · 5 min對照六題檢查清單，寫下答不出來的那一題。
    課堂用檔：卡片分類板、流程圖（FigJam）、Auto Layout 與 Wireframe。全程只能用黑白灰，加一個藍色標重點。詳細步驟見練習頁 ①、練習頁 ②。

    回家作業

    把功能清單、IA 圖、Flow 與 Wireframe 都補完

    這是整條「產品設計流程」的完整交件，涵蓋 Functional Map、IA 圖、Flowchart 與 Wireframe。

    • 看完 Information Architecture — 3 Key Models（NN/g，約 5 分鐘）。
    • 選一個網站逆向拆解 Sitemap（至少 3 層、20 個節點），對照自己的專題修正功能清單與 IA 圖。
    • 把課堂上的 Flowchart 補完整：六種例外路徑一條都不能少。
    • Wireframe 補到 3–5 個畫面，至少涵蓋一個關鍵的例外狀態，每張旁邊寫下六題檢查清單的答案。
    • 主要容器與重複元件用 Auto Layout 做，交件前把 Frame 拉寬拉窄各一次，看會不會爆版。
