01

這堂課在整條流程的哪裡

Unit 05 你畫了一張 IA 圖，把功能分好類、標出核心路徑。那張圖告訴別人「這個產品有哪些東西、放在哪一層」，但它沒有告訴任何人使用者實際上怎麼走。

IA 圖像是一張捷運路線圖：你看得到有哪些站、怎麼轉乘。但「從家裡到公司該怎麼走」是另一件事——那才是流程圖要回答的。

Unit 05 IA 圖與功能清單 → Unit 06 Flowchart、User Flow、初版 Wireframe → Unit 07 Wireframe 細修 → Unit 10 高保真 Mockup。

作業 5「Flowchart + UI Flow + Wireframe」是 Unit 06 跟 Unit 07 合起來完成的，最後交件是 1 張 Flow 加 3–5 個 Wireframe。這個單元先把流程與初版畫面做出來，細修留給下一堂。

02

先把四個詞分開

User Journey、User Flow、Flowchart、Wireflow——這四個詞在網路文章裡常常混著用。開會的時候你說 A、對方腦中想的是 B，討論就會空轉半小時。

分法其實很簡單：前兩個是尺度，後兩個是畫法。這是課堂上用來理清關係的整理法，不是業界所有文件都照這樣分類——看別人的文件時還是要看他怎麼定義。

User Journey 與 User Flow：兩種尺度

NN/g 的定義是這樣的。User Journey 是「使用者為了達成一個高層目標所走過的、以情境為基礎的步驟序列」；User Flow 則是「一組互動，描述在產品裡完成某個常見任務所需要的典型或理想步驟」。

用外送 App 舉例：肚子餓到吃飽是 Journey，中間可能包含看到朋友限動、想起某家店、Google 評價、打開 App、下單、等外送、吃完評分。打開 App 到按下送出訂單是 Flow。

面向User Journey（Unit 04 做過）User Flow（這個單元）
尺度宏觀，看整段體驗微觀，看一個任務
時間數天、數週、數月數分鐘到數小時
範圍跨通路，廣告、朋友、客服電話都算只在產品裡面
畫什麼行動、情緒、想法、接觸點操作與系統的回應
產出物旅程地圖Wireflow、Flowchart、Task diagram
資料來源田野研究、日記研究、訪談可用性測試、後台數據

兩者不是二選一的關係。Flow 是 Journey 裡某一段的放大——你在旅程地圖上標紅的那個痛點，放大之後就是這堂課要畫的 Flow。

Flowchart 與 Wireflow：兩種畫法

同一條 User Flow，可以用不同格式畫出來。而這兩種格式各自看不到一些東西。

Flowchart 的盲點

邏輯分支再完整，都缺少畫面脈絡。「選擇付款方式」在圖上是一個方塊，但實際上是整頁跳轉、還是底部彈出？使用者的感受差很多，圖上看不出來。

Wireframe 的盲點

版面畫得再清楚，都不擅長記錄互動。尤其頁面沒換、內容卻變了的情況——點篩選器之後列表就地更新，一張張靜態畫面表達不出來。

Wireflow 就是為了補這兩個洞而出現的：它把 wireframe 風格的版面設計，跟簡化過的流程圖式互動表示法結合起來。用畫面設計取代抽象符號，讓討論的焦點留在使用者實際會操作的東西上。

畫 Wireflow 有幾個要注意的地方：每個節點呈現的是畫面狀態，可以是整個畫面，也可以只畫有變動的區塊；箭頭要從具體可點的 UI 元件出發，不能只拉一條線；桌機因為畫面大，建議只畫變動的部分，不然圖會大到看不完。

Wireflow 低保真、高保真都能畫。草圖階段拿來想事情，規格階段拿來交付給工程師。它最早是行動 App 團隊發展出來的作法，每個步驟就是一張完整的手機畫面。

上面那張是簡化過的示意圖。想看真實的 Wireflow 長什麼樣，NN/g 原文裡有實際的圖例；UXtweak 的詞條也有一份簡短說明可以對照。

03

什麼時候用哪一種

你的產品長這樣畫這個理由
頁面多、每頁內容相對固定的網站Wireframe重點在每一頁該放什麼；頁面之間的關係用 IA 圖表達就夠了
流程長、分支多、需要窮盡記錄Flowchart邏輯分支是主角，畫面長什麼樣先不重要
頁面少、內容隨互動一直變的 App 或 Web AppWireflow不畫出畫面狀態，就講不清楚「到底哪裡變了」

學生專題大多屬於第三種。所以這堂課的順序是：先用 Flowchart 把邏輯理乾淨，再畫 Wireframe，Unit 07 再把兩者合成 Wireflow。一開始就想直接畫 Wireflow，通常會卡在「邏輯還沒想清楚就要決定畫面」。

04

Flowchart 怎麼畫

工程用的流程圖符號有幾十種，你們不用背。畫使用者流程，四個符號就夠了。

符號代表什麼寫法
◯ 起訖符號起點與終點正式畫法是圓角矩形（膠囊形），課堂上畫成圓形也通。一張圖只有一個起點；終點可以有多個（成功、放棄、失敗）
▭ 矩形動作或畫面用動詞開頭：「輸入手機號碼」，不要寫「手機號碼頁」
◇ 菱形判斷點裡面寫成是非題：「已登入？」不要寫「登入判斷」
→ 箭頭路徑從菱形出去的每一條都要標條件：是／否、成功／失敗
範例板：Flow Chart 流程圖範例。裡面有符號說明區，以及「鬧鐘」與「會員登入」兩個畫完整的流程——後者含忘記密碼、驗證碼、密碼錯三次這些分支，正好可以看例外路徑怎麼接。

注意那份多示範了一個「資料輸出／輸入」的平行四邊形（工程流程圖的符號）。你們畫使用者流程用不到，看到不用理它。
最常見的錯：菱形只畫「是」那一條線出去。如果一個判斷點只有一條路徑，那它就不該是判斷點——把它改成矩形，或者去想清楚「否」的時候會怎樣。

一條流程要交代三件事

◯ 起點：從首頁點「我的課程」 │ ▼ ┌──────────────┐ │ 顯示課程列表 │ └──────────────┘ │ ▼ ◇ 有進行中的課程嗎？ │ ├── 有 ──▶ 顯示上次看到第幾分鐘 ──▶ 點「繼續看」──▶ ◯ 終點：播放器開始播 │ └── 沒有 ─▶ 空狀態：「還沒開始任何課程」＋ 去逛課程的按鈕
  1. 入口：使用者從哪裡進到這條流程？如果不只一個入口（首頁按鈕、推播通知、分享連結），全部畫出來。
  2. 判斷點：中間哪裡會分岔？條件寫清楚。
  3. 終點：怎樣算完成？成功跟失敗要分開畫成兩個終點。

05

最常漏掉的例外路徑

畫流程圖的時候，理想路徑十分鐘就畫完了。剩下的時間全部花在這一節的東西上——而評圖的時候，老師問的也都是這些。

狀況要問自己畫面上會是什麼
沒資料第一次使用的人打開這一頁，看到什麼？空狀態：一句說明 + 一個引導動作
找不到搜尋沒結果、篩選之後一個都不剩？無結果頁：放寬條件的建議、熱門推薦
沒權限沒登入、沒付費、帳號被停用？擋在哪一步、擋下來之後給什麼出路
出錯網路斷掉、付款失敗、檔案太大？錯誤訊息要說「怎麼辦」，不是只說「失敗」
要等需要載入三秒以上的地方？載入狀態、進度提示
反悔中途想退出、想改剛剛填的？返回、取消、編輯的入口

這六條當檢查表用。畫完理想路徑之後，一條一條問自己「這個情況我畫了嗎」。第一次做通常會漏掉好幾種，這很正常，逐條核對就補得回來。

為什麼重要：這些狀態在 Wireframe 階段補，成本是多畫幾個灰階方塊。等到 Mockup 或切版才發現，成本是整個版面重排。

06

從 IA 圖轉成 Flow

  1. 挑一條。從 IA 圖上標了顏色的核心路徑挑一條，不要一次畫全部。
  2. 拆步驟。把這條路徑拆成使用者實際會做的動作，動詞開頭。
  3. 找分岔。每一步問一次「這裡會不會有人走不下去」，會的話就是判斷點。
  4. 補例外。拿上一節那六條逐一補上。
一堂課能畫完一條完整的核心路徑就夠了。畫三條半成品，不如一條把例外都補齊——半成品的流程圖沒辦法拿來畫 Wireframe，因為你不知道要畫幾個畫面。

07

Wireframe 在回答什麼問題

只有三個問題：這一頁要放哪些資訊、使用者可以做哪些動作、下一步在哪裡。其他都先不管。

Wireframe 是灰階方塊，看起來很陽春，這是刻意的。看到彩色跟圖片，所有人的注意力都會跑到「這個藍色好看嗎」，而不是「這裡少了一個返回按鈕」。

學生最常做的事：Wireframe 畫到一半忍不住開始調圓角、選字體、找圖片。一旦開始，這張圖就不再是 Wireframe 了，而是一張很醜的 Mockup——兩邊的好處都拿不到。

08

保真度：三個可以分開調的維度

很多人以為保真度就是「畫得精不精緻」，是一條從粗到細的刻度。實際上它是三個可以各自調整的維度——你完全可以做出一個視覺很粗糙、但互動很完整的原型。

維度低保真高保真
互動 Interactivity需要有人在旁邊手動換畫面連結與選單真的點得下去
視覺 Visuals手繪草圖、灰階方塊完整的層級、間距、版面
內容 Content摘要與佔位符真實的文案與圖片

各自的好處

低保真高保真
準備時間快，省下的時間可以多迭代幾輪慢，做一版就用掉不少時間
測試中途當場拿筆畫一畫就改好了要回去改檔案，下一場才能用
受測者壓迫感低，比較不怕做錯，更願意給負面回饋當成真的軟體在用，行為更接近真實
能測到什麼概念、流程順不順、資訊夠不夠特定元件、工作流程、可視線索、易讀性
測試時誰在忙設計師要一邊操作原型一邊觀察，容易分心也容易操作失誤原型自己會動，設計師可以專心觀察使用者
設計師心態還沒投入太多，願意打掉重來做很久了，捨不得改
利害關係人看得出還沒完成，預期還會再改容易誤以為快做完了

最後兩列才是關鍵。高保真真正的成本不是工時，是你捨不得改。投入越多，越傾向於說服自己「這樣其實也還好」，而不是把它砍掉。

為什麼這個單元刻意停在低保真

  • 畫面一漂亮，評圖的回饋就會全部集中在配色跟字體，結構問題被蓋住。
  • 結構問題留到 Mockup 才發現，要重畫的量是現在的十倍。
  • 你自己也會捨不得——花三小時調好的版面，誰想砍掉重來。
這堂課的規則：只能用黑、白、灰。要標重點就用一個藍色，只准一個。內容維度例外——文字要用真的，見下一節。

09

Wireframe 上該放什麼

要放

真實的標題與按鈕文字、資訊的先後順序與分組、每一個可以點的東西、這一頁唯一最明顯的主要動作、空狀態與錯誤狀態的版本。

先不要放

顏色、漸層、陰影、真實照片（用灰方塊加一個叉代替）、精挑的字體、圖示細節（畫個圈標「icon」就好）、動畫與轉場。

文字一定要用真的。Lorem ipsum 會騙你——假字排起來永遠很整齊，等到真的標題塞進去才發現會爆版、或者短到留一大片空白。按鈕也一樣，寫「加入購物車」，不要寫「按鈕」。

可以用現成的元件庫

不用每個方塊都自己畫。Wireframe Web UI Kit 收了大量現成區塊——導覽列、Hero、卡片列表、表單、頁尾，桌機與手機尺寸都有，命名是「類型＿編號＿寬度」。

它適合拿來當零件來源（找接近的區塊複製過來改）、當參考（卡住時看看這種頁面通常有哪些區塊）、以及當 Auto Layout 範例（拆開別人做好的區塊，看它哪一層用 Hug 哪一層用 Fill）。

但順序不能反過來。先看流程圖決定這一頁要放什麼，再去元件庫找對應的區塊；不是先看庫裡有什麼，再回頭決定頁面長怎樣。判斷方式：如果你選某個區塊的理由是「它看起來不錯」而不是「我的流程需要這個」，那就是反過來了——這樣等於把這個階段要練的結構思考跳過去。

另外，Kit 裡的區塊通常比低保真再精緻一點。複製過來之後把顏色拿掉、圖片換成灰方塊，維持黑白灰。

畫完一張，問自己這六題

  1. 第一眼會看到什麼？那是這一頁最重要的東西嗎？
  2. 這一頁的主要動作是哪一個？它有比其他按鈕明顯嗎？
  3. 使用者從哪裡來的？他知道自己在哪一層嗎？
  4. 如果這裡沒有資料，畫面長什麼樣？
  5. 按下去之後會發生什麼？成功跟失敗分別看到什麼？
  6. 想回上一步的話，回得去嗎？
六題都答得出來，這張 Wireframe 才算畫完。答不出來的那一題，通常就是流程圖上漏掉的那條線——回去補流程圖，不要在畫面上硬掰。

10

Figma Auto Layout

沒用 Auto Layout 的時候，元素靠絕對座標擺放：你把標題改成兩行，下面所有東西都要手動往下推。用了之後，它們自己會讓開。

Auto Layout 讓 frame 隨內容變動自動反應——裡面的元素會依照方向、間距、內距、對齊自動排列。快捷鍵是選好圖層按 ⇧ A（Windows 是 Shift A）。

三種排列方向

方向行為典型用途
垂直 Vertical沿 y 軸往下排清單、表單欄位、卡片內部的標題與說明
水平 Horizontal沿 x 軸往右排，可設定換行按鈕列、標籤列、導覽項目
網格 Grid排成行與列，格子可跨欄商品列表、儀表板

實務上幾乎都在巢狀使用：一張商品卡內部是垂直（圖片／標題／價格），一排卡片是水平或網格。每一層 frame 各自有獨立的 padding 與 gap。

Padding 與 Gap

兩個都是留白，差別在留在哪裡。這兩個搞混，版面就會怎麼調都不對。

┌─────────────────────────────────┐ ◀── 容器邊界 │ ↕ padding-top │ │ ┌─────────────────────────┐ │ │ │ 項目 A │ │ │ └─────────────────────────┘ │ │ ↕ gap │ │ ┌─────────────────────────┐ │ │ │ 項目 B │ │ │ └─────────────────────────┘ │ │ ↕ padding-bottom │ └─────────────────────────────────┘ ↔ padding-left padding-right ↔
  • Padding：容器邊緣與裡面東西之間的留白。可以四邊統一、上下左右分開，或四個值各自設定。
  • Gap between：裡面的東西彼此之間的距離。給固定數值，或設成 Auto 讓它們平均散開。

三種尺寸模式

這是 Auto Layout 最容易卡住的地方。先記一句話：Hug 只能給容器，Fill 只能給裡面的東西。

模式能套在誰身上行為什麼時候用
Hug contents只有 Auto Layout 容器縮到剛好包住內容按鈕：文字多長，按鈕就多寬
Fill container只有子元件撐滿父容器剩下的空間（會遵守間距設定）輸入框：不管視窗多寬都填滿
Fixed容器與子元件都可以尺寸固定不變頭像、圖示這類固定尺寸的東西
一定要記住這條規則：只要 Auto Layout 容器裡有任何一個子元件設成 Fill container，容器在那個軸向就不再是 Hug，會自動變成 Fixed。「我明明設了 Hug 怎麼沒反應」，九成是這個原因。

另外可以疊加最小／最大尺寸限制。兩個最常用的時機：文字容器加 max width，避免視窗拉很寬時一行變成八十個字；卡片或區塊加 min height，避免內容很少的時候整塊塌掉。作業的壓力測試如果發現拉寬會爆版，通常就是少了這兩個其中之一。

Absolute position：跳出排列流程

有些東西不該排在流程裡——例如卡片右上角的收藏愛心、蓋在圖片上的標籤。把它設成 absolute position，它會留在 frame 內但不參與排列，位置相對於父容器精確定位。Mac 按住 Ctrl 拖曳，Windows 按住 S 拖曳。

Constraints 與 Auto Layout 的分工

Constraints 管的是另一件事：當 frame 被拉大拉小的時候，圖層要怎麼跟著動。

設定水平方向的行為
Left / Right與左邊界（或右邊界）保持固定距離
Left and Right兩邊都固定，所以圖層自己會變寬變窄
Center永遠對齊 frame 的水平中線
Scale尺寸與位置都按 frame 的比例縮放

垂直方向同理：Top、Bottom、Top and Bottom、Center、Scale。

兩套機制是獨立的。Auto Layout 容器裡的一般子元件用不了 Constraints——它們用的是 Hug／Fill／Fixed。只有設成 absolute position、跳出排列流程的元件，才會回到 Constraints。

什麼時候會用到 Constraints：做多裝置的響應式版面、frame 縮放時要維持元素位置、控制巢狀 frame 內部的行為。Unit 09 做 Web 多斷點版面的時候會再深入。

12

課堂練習與回家作業

課堂練習：從你自己的 IA 圖開始（80 分鐘）

個人作業，用自己的專題。四階段結束後另有 15 分鐘各組成果分享。

  1. 拆步驟（15 分）：從 IA 圖挑一條核心路徑，拆成使用者的動作。
  2. 畫 Flowchart（20 分）：補上判斷點與六種例外路徑。
  3. Auto Layout 練手（20 分）：做一張卡片，再排成一個列表。
  4. 畫 Wireframe（25 分）：3 個低保真畫面，涵蓋流程的頭、中、尾。

回家作業：作業 5（上半）

  1. 把課堂上那條 Flowchart 補完整，六種例外路徑一條都不能少。
  2. Wireframe 補到 3–5 個畫面，整組至少涵蓋一個關鍵的例外狀態。
  3. 每張 Wireframe 旁邊寫下六題檢查清單的答案。
  4. 主要容器與會重複的元件用 Auto Layout 做，交件前把 Frame 拉寬拉窄各一次，看會不會爆版。
  5. 行有餘力再畫第二條與第一條交會的 Flow，這是加分項，不是必要。
繳交：Figma 連結一份，含 1 張 Flow 與 3–5 個 Wireframe，對應課綱作業 5 的交件規格。完整步驟與配分見練習頁，交件清單見繳交清單與評分。

AI 協作提示詞

AI 在這個階段能幫你檢查有沒有漏，但不能幫你決定流程長什麼樣——它不知道你的使用者是誰。以下提示詞都要先貼上你自己的東西再問。

① 檢查流程有沒有漏掉例外

以下是我畫的使用者流程，用文字描述：
[貼上流程步驟，一行一步，分岔的地方寫清楚條件]

我的使用者是：[貼上 Persona 摘要]

請幫我檢查：
1. 這條流程有哪些判斷點是我沒標出來的？
2. 下面六種狀況我分別漏掉了哪些：沒資料、找不到、沒權限、出錯、要等、反悔。
3. 有沒有哪一步，使用者可能不知道下一步要做什麼？
4. 終點只有「成功」嗎？失敗跟中途放棄的終點在哪裡？

請把「流程裡明確缺少的」跟「你的推測」分開列。
不要幫我重寫整條流程，只指出缺口。

② 從流程推出需要哪些畫面

以下是我補完例外路徑之後的流程：
[貼上完整流程]

請幫我整理：
1. 這條流程總共需要幾個畫面？各自是什麼？
2. 哪些是同一個畫面的不同狀態（例如空狀態、載入中、錯誤），
   不需要另外算一個畫面？
3. 如果只能先畫 3 個，你建議畫哪 3 個？為什麼？
4. 每個畫面上必須有的資訊與動作各是什麼？

只根據我提供的流程分析，不要自行新增我沒寫的功能。

③ 檢查 Wireframe 的資訊層級

以下是我某一張 Wireframe 上，由上到下的所有元素：
[一行一個元素，照實際順序寫，標註哪些是可點的]

這一頁的主要任務是：[一句話]

請幫我檢查：
1. 最重要的資訊有沒有排在使用者第一眼會看到的位置？
2. 這一頁有幾個可點的東西？主要動作夠不夠明顯，還是被淹沒了？
3. 有沒有哪些元素其實跟主要任務無關，可以拿掉？
4. 依這個順序，使用者讀完會知道下一步要做什麼嗎？

只根據我列出的元素判斷，不要假設畫面上還有其他東西。
使用界線：不要讓 AI 直接生成流程圖或 Wireframe。它不知道你的使用者研究結果，產出的會是「一般電商大概長這樣」的通用版本——那跟你前四個單元做的研究完全脫鉤，評圖時很容易被看出跟研究資料脫節。
