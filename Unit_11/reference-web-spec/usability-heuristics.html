H1 · Visibility of System Status

系統狀態可見性

系統應在合理的時間內，透過適當的視覺回饋讓使用者了解目前發生了什麼事。使用者不應該猜測——動作是否成功？系統是否還在跑？

沒有回饋 = 使用者焦慮 = 反覆點擊 = 更多錯誤
良好範例
Gmail — 寄信 Toast 提示
郵件寄出後立即出現「郵件已傳送」Toast，並附上「復原」按鈕倒數 5 秒。使用者明確知道動作成功，且可以反悔。
良好範例
YouTube — 上傳進度條
上傳影片時顯示藍色進度條 + 百分比數字 + 預估剩餘時間，使用者知道還要等多久，不會誤以為當機。
反例警示
舊版銀行網站 — 轉帳後頁面空轉
按下「確認轉帳」後頁面無任何反應，沒有 Loading 動畫也沒有成功訊息。使用者不確定交易是否執行，傾向重複提交。

H2 · Match Between System and the Real World

現實世界對應

使用使用者熟悉的語言、詞彙與隱喻，而非系統導向的術語。圖示、語言和概念都應對應到使用者的既有認知，讓他們「不需要學習」就能直覺操作。

好的隱喻讓使用者用既有知識理解新事物，學習成本趨近於零
良好範例
iPhone — 實體隱喻圖示
電話聽筒 = 撥打電話、垃圾桶 = 刪除、購物車 = 待結帳商品。所有圖示都有現實原型，即使是第一次使用智慧型手機的長輩也能理解。
良好範例
Google Maps — 空間導航語言
「藍點 = 你在這裡」、指南針對應真實方向感、路線用箭頭標示——完全對應人類閱讀實體地圖的習慣。
反例警示
系統錯誤訊息 — 工程師語言
顯示「HTTP 403 Forbidden」或「ECONNREFUSED」——這是工程師的語言，對一般使用者毫無意義，無法產生任何心智對應。

H3 · User Control and Freedom

使用者控制與自由

使用者常會誤觸或做出錯誤決定，系統需提供明顯的「緊急出口」讓他們隨時後悔。這不是在縱容粗心，而是讓使用者敢大膽探索的安全感來源。

「緊急出口」設計得越清楚，使用者就越敢嘗試新功能
良好範例
Gmail — 復原寄送功能
寄出後可在設定的秒數內（5/10/20/30 秒可調）點「復原」取消。這讓使用者在寄信時更放心，即使寄錯也有救。
良好範例
Mac — 垃圾桶機制
刪除檔案不會立即永久消失，而是移至垃圾桶，使用者可隨時還原。需要「永久清除」才是不可逆的操作，且有二次確認。
反例警示
某訂閱 App — 取消訂閱流程
取消訂閱入口藏在設定的第 5 層選單中，還需點過「保留訂閱」、「確定離開」等多個障礙頁面，被設計成讓使用者找不到出口。

H4 · Consistency and Standards

一致性與標準

相同的動作、詞彙、圖示在整個產品中應保持一致，並遵循平台設計規範（iOS HIG / Material Design）。打破一致性就等於強迫使用者重新學習，增加認知負擔。

一致性讓使用者把腦力花在任務上，而不是花在搞懂介面上
良好範例
iOS — 全系統「返回」一致性
無論第三方 App 還是原生 App，「返回上一頁」統一在左上角，手勢也統一是右滑。使用者只需學一次，適用所有 App。
良好範例
Google Workspace — 分享按鈕
Docs、Sheets、Slides、Drive 的「分享」按鈕位置、顏色（藍色）、文字完全相同。跨產品使用時零學習成本。
反例警示
介面內部不一致
同一個 App 裡，購物頁面「確定」在右側，結帳頁面「確定」跑到左側；「取消」有時是按鈕，有時是連結文字——每次都讓使用者多想一秒。

H5 · Error Prevention

錯誤預防

比起設計漂亮的錯誤訊息，防止錯誤發生才是更好的設計。設計應在可能出錯的地方加上護欄：限制輸入、二次確認、語境提示，讓使用者根本無法犯那個錯。

限制 > 確認 > 修復 ── 越早攔截錯誤，代價越低
良好範例
Google 日曆 — 日期選擇器
以點選月曆取代手動輸入日期，根本不讓使用者輸入「2月30日」這種不存在的日期，從源頭排除格式錯誤。
良好範例
GitHub — 刪除 Repository 二次確認
刪除 Repo 前必須手動輸入完整的 Repository 名稱才能啟用刪除按鈕。主動的確認行為讓誤刪幾乎不可能發生。
反例警示
Outlook — 全部回覆的致命鄰居
「回覆」與「全部回覆」按鈕緊鄰放置，圖示極為相似。每年都有人誤按全部回覆，把私人訊息發給整個部門或公司通訊錄。

H6 · Recognition Rather Than Recall

辨識而非記憶

減少使用者的記憶負荷，將選項、物件和動作可視化。使用者不應需要記住前一個頁面的資訊才能完成目前的任務——讓系統記住，不要讓人記住。

辨識（從選項中找到）比回憶（從記憶中提取）的認知成本低 10 倍
良好範例
Google 搜尋 — 自動完成
輸入前幾個字，系統立即顯示候選搜尋詞。使用者不需記住完整關鍵字，也不需知道正確拼法，「看到就認得出來」就夠了。
良好範例
Spotify — 最近播放 / 推薦
首頁直接顯示最近聽過的歌單和藝人，使用者不用記住自己喜歡的歌單叫什麼名字，看到封面圖就能辨識。
反例警示
舊版 Windows — 執行視窗
「Win + R」打開空白執行框，要使用者自行記住 cmd、regedit、msconfig、devmgmt.msc…… 沒有任何提示，完全仰賴記憶。

H7 · Flexibility and Efficiency of Use

彈性與效率

系統應同時兼顧新手與專家。為新手提供清晰引導；為專家提供快捷鍵、批次操作和個人化設定，讓高頻使用者能更快完成任務，不必每次都走完整流程。

新手走寬路，專家走捷徑 ── 好設計讓兩者都滿意
良好範例
Figma — 鍵盤快捷鍵體系
V = 選取工具、R = 矩形、T = 文字、Cmd+G = 群組、Alt+拖曳 = 複製。熟練後完全不需碰側邊欄，設計速度提升數倍。
良好範例
VS Code — Command Palette
Cmd+Shift+P 打開命令面板，輸入任意關鍵字就能執行所有功能。專家不需記住選單路徑，用語言直接調用任何命令。
反例警示
無快捷機制的 ERP 系統
每筆訂單都需從頂部導覽列逐層點選，沒有快捷鍵、沒有常用書籤、沒有批次處理。每天使用 200 次的員工和第一次使用的人走完全一樣的路徑。

H8 · Aesthetic and Minimalist Design

極簡美學設計

介面上的每個元素都應有其存在理由。多餘的資訊不只是無用，而是在稀釋重要資訊的能見度。每增加一個不必要的元素，核心訊息就被削弱一分。

刪去一個不必要的元素，整體設計就進步了一步
良好範例
Google 首頁
Logo + 搜尋框 + 兩個按鈕，就是整個頁面的全部。沒有廣告欄、沒有導覽列、沒有推薦內容。所有視覺注意力都被引導到唯一的任務：搜尋。
良好範例
Apple 產品頁
大圖、少量精煉文字、大量留白。每個畫面只傳遞一個核心訊息，讓使用者的眼睛自然地被引導，而非被迫在資訊叢林中尋找。
反例警示
早期 Yahoo 首頁
新聞頭條、天氣、股市、廣告 Banner、郵件入口、熱門搜尋……全部擠在同一個頁面。使用者的眼睛無從聚焦，沒有任何資訊是重要的。

H9 · Help Users Recognize, Diagnose, and Recover from Errors

錯誤識別與修復

錯誤訊息應以使用者看得懂的語言準確指出問題，並提供明確的解決方向。好的錯誤訊息包含三個要素：發生了什麼、為什麼發生、怎麼解決。

好的錯誤訊息 = 問題是什麼 + 為什麼 + 怎麼修
良好範例
Airbnb — 表單驗證訊息
「請輸入有效的電子郵件地址，例如 name@example.com」— 具體說明錯在哪裡，並直接給出正確格式示範，使用者一看就知道怎麼改。
良好範例
GitHub — 404 錯誤頁面
幽默插圖 + 清楚說明（頁面不存在）+ 搜尋框 + 「回到首頁」按鈕。使用者迷路了，但有明確的出口，不會被卡死在錯誤頁面。
反例警示
無意義的系統錯誤代碼
只顯示「Error 0x80070005」或「操作失敗」—— 使用者完全不知道哪裡錯、為什麼錯，也不知道下一步該做什麼，只能重試或放棄。

H10 · Help and Documentation

說明文件

雖然最好的介面不需要說明就能使用，但當使用者真的卡住時，說明要易於找到、易於搜尋，且以使用者的任務為導向——而不是以功能或系統架構為導向。

最好的說明出現在需要它的當下
良好範例
Notion — 空狀態引導文字
空白頁面上顯示「輸入 / 以選擇區塊類型」的淡灰提示文字。新用戶第一秒就知道怎麼開始，不需要看任何說明文件。
良好範例
Figma — 情境式說明
Help Center 可全文搜尋；UI 中的 ? 圖示直連相關說明頁；複雜功能有影片示範。說明跟著你走，不是你去找說明。
反例警示
說明文件藏在頁尾的企業系統
說明連結藏在頁尾 10px 的灰色文字中；或說明文件全是工程師寫的技術術語，有效資訊需要在 20 頁 PDF 中自行尋找。
